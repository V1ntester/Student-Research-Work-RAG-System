# Решения, ADR и открытые вопросы

> **Простыми словами.** Принятые архитектурные решения с причинами (ADR) и список вопросов, на которые пока нет ответа (OPEN), — с указанием, кто должен ответить и к какому моменту.

Этот файл — единый небольшой реестр. При росте отдельный ADR можно вынести в файл с сохранением ID. Ни один ADR сейчас не имеет APPROVED: согласованы направления (ADR-004 — предварительно), а реализация не разрешена.

## ADR-001 — Модульный Backend и файловые артефакты

- Дата: 2026-10-11.
- Статус: CONFIRMED на уровне первоначальной концепции; источник SRC-002.
- Контекст: исследовательский MVP, приложение ещё отсутствует, нет подтверждённой потребности в постоянных пользовательских данных.
- Альтернативы: один файл со всей логикой; модульный монолит; отдельные микросервисы. Хранение: файлы либо БД.
- Согласованное направление: Frontend, одно Backend-приложение с отдельными модулями подготовки корпуса/retrieval/generation, файловые артефакты корпуса и индекса без БД.
- Причины: явные границы и тестируемость при небольших затратах на запуск; БД не нужна только ради наличия моделей данных.
- Последствия: контракты внутри Backend нужны с первого этапа; постоянная история/параллельное редактирование корпуса могут потребовать нового решения. Форматы файлов и стек ещё не выбраны.
- Связи: REQ-007, REQ-014; ARCH-BACKEND-001; OPEN-005, OPEN-007.

## ADR-002 — Самостоятельные вопросы и ответ целиком

- Дата: 2026-10-11.
- Статус: CONFIRMED на уровне первоначальной концепции; источник SRC-002.
- Контекст: нужно оценить retrieval без дополнительной неоднозначности диалоговой памяти.
- Альтернативы: самостоятельный запрос; передача всей истории; переписывание запроса на основе истории. Доставка: полный ответ либо streaming.
- Согласованное направление: вопрос независим от предыдущих; UI показывает историю вкладки; ответ приходит целиком.
- Причины: проще воспроизводить входы, контролировать prompt и проверять состояния/ошибки.
- Последствия: менеджер должен назвать объект и условия в самом вопросе; невозможен полноценный многоходовый разговор. Макет и эксперт могут потребовать пересмотра.
- Связи: RULE-CHAT-001; API-CHAT-001; OPEN-001.

## ADR-003 — Подготовка корпуса вне веб-интерфейса

- Дата: 2026-10-11.
- Статус: CONFIRMED на уровне первоначальной концепции; источник SRC-002.
- Контекст: формат документов и процессы обновления не известны; нужна воспроизводимая база эксперимента.
- Альтернативы: заранее подготовленный индекс; отдельная операция подготовки; web-upload с администрированием.
- Согласованное направление: оператор готовит корпус и индекс отдельной операцией; чат работает с готовым снимком.
- Причины: нет необходимости проектировать права, UI загрузки и обработку фоновых задач.
- Последствия: обновление требует оператора; загрузка нового корпуса не является пользовательским сценарием чата. Атомарное построение и переключение после перезапуска — DRAFT, SRC-003.
- Связи: REQ-007; ARCH-RAG-001; BEH-INDEX-001; OPEN-002, OPEN-004.

## ADR-004 — Две базы знаний по режимам «Спросить» и «Продавать»

- Дата: 2026-10-19.
- Статус: CONFIRMED как предварительное направление; источники SRC-007 (замысел автора макета) и SRC-008 (пользователь: «Предварительно вносим изменение для двух баз знаний»). Детали ниже DRAFT/PROPOSED, SRC-003. APPROVED нет.
- Контекст: в макете SRC-005 есть переключатель режимов. По словам автора макета, режимы используют для ответа разные базы. До этого спецификация предполагала один корпус.
- Альтернативы: один корпус с фильтром по метке документа; два независимых корпуса и индекса; поиск по обеим базам со смешиванием результатов.
- Согласованное направление: у каждого режима своя база знаний. Режим выбирает базу, поиск идёт только в ней.
- Предложенные детали (не согласованы): каждая база собирается отдельной операцией в собственный снимок с собственным index_version; режим — обязательное поле запроса; без автоматического перехода в другую базу при отсутствии кандидатов; оценка ведётся раздельно по базам.
- Причины: разделение сохраняет воспроизводимость каждого снимка, позволяет оценивать базы по отдельности и не смешивает рабочие материалы разного назначения.
- Последствия: оператор готовит и публикует две базы; Backend при запуске выбирает снимок для каждой; готовность одной базы не зависит от другой. Состав баз, допустимость одинаковых документов в обеих и различия формата ответа между режимами не определены (OPEN-010).
- Связи: REQ-018; RULE-RAG-002, RULE-RAG-004; BEH-CHAT-016, BEH-INDEX-001; API-CHAT-001, API-SOURCE-001; UI-CHAT-005; ARCH-RAG-001, ARCH-RAG-002, ARCH-BACKEND-002; OPEN-010, OPEN-011.

## Порядок закрытия вопроса

Зафиксировать ответ, источник/дату и область согласования; указать затронутые ID; предложить изменения; получить нужное подтверждение; обновить спецификации и историю. Сохранить OPEN как закрытую запись со ссылкой на решение. Молчание не является ответом. Уточнение одного параметра не разрешает реализацию всего MVP.

## Шаблон нового ADR

ID; дата; статус; источник; контекст; альтернативы; предложенное либо принятое решение (явно различать); причины; последствия; связанные требования и OPEN; подтверждение человека. Пока решение не подтверждено, поле «принятое решение» не заполнять как факт.
