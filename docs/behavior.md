# Поведенческая спецификация

Основной источник истины для наблюдаемого поведения. Все сценарии этого файла: DRAFT, источник SRC-003 — детализация согласованной концепции SRC-002. Проверки ниже запланированы, не реализованы и не выполнены. Предметная правильность ответов требует отдельной экспертной оценки.

## Состояния и общие условия

Предлагаемые состояния: ready → processing → answer / partial / insufficient / clarification / conflict / error / result_unknown. Все конечные состояния допускают новый вопрос. Непустой допустимый вопрос переводит в processing; открытие источника не меняет состояние вопроса. Обработка одного запроса не блокирует чтение прежних сообщений.

Предусловие успешных сценариев: готов согласованный снимок индекса, конфигурация валидна, вопрос в лимите. Значения лимитов OPEN-008 задаются до реализации. Контракт исходов и ошибок: [API](backend/api.md). Инварианты: [rules.md](rules.md). Независимость вопросов: RULE-CHAT-001.

### BEH-CHAT-001

**Отправка вопроса и полный ответ.** REQ-001, REQ-002, REQ-003, REQ-006; RULE-INPUT-001, RULE-RAG-001, RULE-RAG-002, RULE-GEN-001; UI-CHAT-001, UI-CHAT-002, UI-CHAT-003; API-CHAT-001; TEST-CHAT-001.

Given: чат готов, вопрос допустим, управляемый корпус содержит достаточные сведения.

When: пользователь отправляет вопрос кнопкой или согласованным клавиатурным действием.

Then:
- Вопрос один раз появляется в списке сообщений; поле черновика очищается после принятия UI.
- UI показывает processing и не допускает второй отправки до завершения текущей.
- Backend проверяет вопрос, выбирает один снимок, выполняет BM25, отбор контекста и генерацию.
- Результат answer появляется целиком с непустым текстом и хотя бы одним источником; processing завершается.
- Изменение предыдущих сообщений/истории UI не влияет на вход данного поиска.

Приёмка: для фиксированного корпуса и управляемого генератора переданный контекст совпадает с retrieval; результат принадлежит отправленному вопросу, а не другому сообщению. Достоверность реальной LLM оценивается по протоколу, не точным совпадением строки.

### BEH-CHAT-002

**Пустой вопрос.** REQ-001; RULE-INPUT-001; UI-CHAT-001; TEST-CHAT-002.

Given: поле пусто или содержит только крайние пробельные символы.

When: пользователь пытается отправить его.

Then: сетевой запрос не создаётся, состояние остаётся ready, показана подсказка «Введите вопрос». Прямой запрос к API с таким значением возвращает 400/INVALID_QUESTION и не вызывает retrieval/LLM.

Приёмка: одинаковая проверка смыслового ограничения на Frontend и Backend; отсутствие сетевого запроса проверяется только для UI.

### BEH-CHAT-003

**Превышение длины.** REQ-001, REQ-011; RULE-INPUT-001; UI-CHAT-001; TEST-CHAT-003.

Given: длина после trim превышает MAX_QUESTION_CHARS.

When: выполняется отправка.

Then: UI сообщает допустимый предел, текст остаётся для редактирования; прямой API возвращает 400/QUESTION_TOO_LONG. При ровно MAX_QUESTION_CHARS вопрос проходит эту проверку. Backend не вызывает retrieval/LLM для превышения.

Приёмка: граничные значения max−1/max/max+1 и Unicode-кодовые точки. Значение max ещё не выбрано.

### BEH-CHAT-004

**Нет кандидатов.** REQ-002, REQ-005; RULE-RAG-003; UI-CHAT-003; TEST-CHAT-004.

Given: готовый индекс не даёт кандидатов по [политике retrieval](rag/retrieval.md).

When: обрабатывается допустимый вопрос.

Then: ответ HTTP 200 с outcome=insufficient, reason=no_candidates, sources=[]; LLM не вызывается. UI сообщает «В доступных материалах не найдены сведения для ответа» и предлагает уточнить объект или формулировку.

Приёмка: этот исход не содержит технической ошибки и не утверждает, что искомого знания не существует вообще.

### BEH-CHAT-005

**Неполные данные.** REQ-003, REQ-005; RULE-GEN-001, RULE-SOURCE-001; TEST-CHAT-005.

Given: вопрос состоит из двух частей, контекст подтверждает ответ только на одну.

When: генератор возвращает корректный исход partial.

Then: UI показывает подтверждённую часть с источниками и явно указывает часть, для которой сведений недостаточно; не помечает результат полным ответом. Если никакая часть не подтверждается, допустим только insufficient.

Приёмка: технический тест использует управляемый генератор; эксперт проверяет полноту/отсутствие домысливания на реальной модели. Не требуется автоматический семантический классификатор.

### BEH-CHAT-006

**Индекс или поиск недоступен.** REQ-002, REQ-006; RULE-ERROR-001; TEST-CHAT-006.

Given: снимок не готов либо retrieval падает.

When: приходит допустимый вопрос.

Then: 503/INDEX_NOT_READY либо 503/RETRIEVAL_UNAVAILABLE; LLM не вызывается. UI показывает error, сохраняет вопрос и допускает явный повтор; не показывает insufficient. Технические подробности пользователю не раскрываются.

Приёмка: разные коды причин, отсутствие ответа, одинаковое безопасное поведение UI.

### BEH-CHAT-007

**Недоступность или таймаут LLM.** REQ-006, REQ-011; RULE-ERROR-001, RULE-REQUEST-001; TEST-CHAT-007.

Given: найден контекст, запрос к LLM не может завершиться.

When: получен отказ провайдера или истёк LLM_TIMEOUT_MS/REQUEST_TIMEOUT_MS.

Then: 503/LLM_UNAVAILABLE или 504/REQUEST_TIMEOUT; UI завершает processing, показывает error и кнопку повтора. Тексты исключений и ответ провайдера не попадают пользователю. Самостоятельного ответа «по памяти» нет.

Приёмка: управляемые отказ и таймаут завершаются в согласованном бюджете; автоматических повторов к провайдеру нет.

### BEH-CHAT-008

**Повторное нажатие отправки.** REQ-006; RULE-REQUEST-001; TEST-CHAT-008.

Given: вопрос обрабатывается в текущем чате.

When: пользователь повторно нажимает кнопку либо клавиатурную отправку.

Then: UI не создаёт второй запрос и не дублирует сообщение. После error или result_unknown явный повтор создаёт новый запрос с новым request_id.

Приёмка: быстрый двойной клик/нажатие вызывает один запрос. Это ограничение UI, не серверная гарантия идемпотентности и не общий лимит на все вкладки.

### BEH-CHAT-009

**Потеря соединения и неизвестный результат.** REQ-006, REQ-011; RULE-REQUEST-001; TEST-CHAT-009.

Given: запрос отправлен, но полный HTTP-ответ не получен.

When: связь прерывается либо истекает CLIENT_TIMEOUT_MS без ответа.

Then: UI переходит в result_unknown, сообщает «Не удалось получить результат. Запрос мог быть обработан», сохраняет вопрос и предлагает явный повтор. Частичный HTTP-ответ не показывается как готовый ответ.

Приёмка: нет автоматической повторной отправки, обещания отмены серверной обработки или гарантии отсутствия повторного расхода LLM. Поздний ответ старого локального запроса не заменяет результат нового: UI проверяет локальную принадлежность операции.

### BEH-CHAT-010

**Просмотр источника.** REQ-004; RULE-SOURCE-001, RULE-UI-001; API-SOURCE-001; TEST-CHAT-010.

Given: показан результат с источником S1, chunk_id и index_version.

When: пользователь открывает S1.

Then: панель показывает название документа, локатор, версию и полный фрагмент из соответствующего снимка. Уже включённый в ответ excerpt остаётся доступным независимо от второго запроса. Получение фрагмента использует точные index_version/chunk_id, не текущую версию по умолчанию.

Приёмка: текст совпадает с зафиксированным фрагментом; путь файловой системы и произвольный URL не раскрываются. Недоступность источника — BEH-CHAT-015.

### BEH-CHAT-011

**Необходимость уточнения.** REQ-003, REQ-005; RULE-CHAT-001; TEST-CHAT-011.

Given: контекст содержит несколько объектов, а самостоятельный вопрос не позволяет выбрать нужный.

When: генератор возвращает корректный clarification с просьбой назвать объект/условие.

Then: UI показывает уточняющий вопрос; пользователь отправляет новый полный вопрос. Предыдущий ответ не становится контекстом автоматически.

Приёмка: управляемый результат имеет нужный исход и не содержит выбранного наугад объекта. Для реальной LLM способность распознать неоднозначность измеряется экспертно. Если retrieval вообще не дал кандидатов, применяется BEH-CHAT-004 с подсказкой уточнить вопрос; детектор местоимений не предполагается.

### BEH-CHAT-012

**Противоречащие сведения.** REQ-003, REQ-005; RULE-GEN-001, RULE-DOMAIN-001; TEST-CHAT-012.

Given: переданный контекст содержит несовместимые утверждения, отсутствует согласованное правило их разрешения.

When: генератор распознаёт противоречие и возвращает conflict.

Then: UI обозначает противоречие, показывает основания и предлагает уточнить у владельца знаний. Система не выбирает источник только по времени файла и не выдаёт один вариант как окончательный.

Приёмка: управляемый ответ корректно отображается; обнаружение противоречий реальной LLM оценивается отдельно. Противоречие вне отобранного контекста система может не увидеть — это ограничение retrieval.

### BEH-CHAT-013

**Перезагрузка и самостоятельность вопросов.** REQ-001, REQ-014; RULE-CHAT-001; TEST-CHAT-013.

Given: в текущей вкладке есть сообщения.

When: пользователь отправляет новый вопрос или перезагружает страницу.

Then: новый запрос содержит только новый question; после перезагрузки история и черновик очищаются. Незавершённый запрос не восстанавливается. Другие вкладки имеют независимое состояние.

Приёмка: отсутствуют записи истории в постоянном клиентском/серверном хранилище. Возможность экспорта истории пока не предлагается.

### BEH-CHAT-014

**Задержка и некорректный ответ модели.** REQ-003, REQ-006, REQ-011; RULE-ERROR-001, RULE-SOURCE-001; TEST-CHAT-014.

Given: запрос обрабатывается дольше UI_WAIT_HINT_MS, но ещё в пределах таймаута; либо LLM возвращает неверную структуру/неизвестный источник.

When: проходит порог подсказки или выполняется проверка результата.

Then: при задержке UI продолжает processing с текстом «Обработка занимает больше времени»; это не отдельная ошибка. При невалидной структуре — 502/INVALID_LLM_RESPONSE, безопасное error, без публикации неподтверждённых ссылок. Автоматической повторной генерации нет.

Приёмка: индикатор не обещает процент готовности; после получения ответа/ошибки таймер подсказки очищается.

### BEH-CHAT-015

**Источник недоступен.** REQ-004, REQ-006; RULE-SOURCE-001; API-SOURCE-001; TEST-CHAT-015.

Given: ответ есть, но запрошенная версия индекса отсутствует либо фрагмент не найден.

When: пользователь открывает источник.

Then: 410/INDEX_VERSION_UNAVAILABLE или 404/SOURCE_NOT_FOUND; панель объясняет недоступность. Ответ и включённый excerpt сохраняются, другой документ не подставляется.

Приёмка: ошибка панели не переводит весь чат в ошибку генерации. При сетевой ошибке панели допустим повтор только чтения источника.

### BEH-INDEX-001

**Успешная подготовка корпуса.** REQ-007, REQ-009; RULE-RAG-001, RULE-RAG-002; TEST-INDEX-001.

Given: есть разрешённый корпус и валидная фиксированная конфигурация.

When: оператор запускает отдельную операцию подготовки.

Then: создаются фрагменты, manifest, индекс и отчёт; проверки целостности пройдены; готовый снимок публикуется целиком. Чат не читает незавершённые артефакты. Новая версия выбирается при отдельном запуске Backend; web-upload отсутствует.

Приёмка: повторная сборка тех же входов даёт те же ID и результаты поиска; runtime в одном запуске использует выбранную версию.

### BEH-INDEX-002

**Ошибочные документы и незавершённая сборка.** REQ-007, REQ-009; RULE-ERROR-001; TEST-INDEX-002.

Given: есть пустой, неподдерживаемый, повреждённый или неизвлекаемый документ либо сбой записи.

When: выполняется подготовка.

Then: отчёт содержит документ и причину отклонения; неполный снимок не становится активным. Базовая предлагаемая политика — не публиковать сборку с отклонёнными входными документами. Оператор может явно исключить их и собрать новый заявленный корпус; исключение фиксируется в manifest, а не происходит молча. Пустой корпус не публикуется.

Приёмка: ранее готовый снимок остаётся пригодным; проблемы корпуса не становятся ответами пользователю. Политика строгой сборки — новая DRAFT-деталь, не ранее согласованное решение.
