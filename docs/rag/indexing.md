# Подготовка документов и индексирование

> **Простыми словами.** Как документы превращаются в базу для поиска: извлечь текст, разбить на фрагменты, построить индекс, проверить и опубликовать готовую версию. Делается заранее оператором, отдельно для каждого режима.

Статус алгоритмических деталей: DRAFT/PROPOSED, SRC-003. Offline-подготовка согласована SRC-002, ADR-003. Фактический состав корпуса OPEN-002 ещё неизвестен; ниже базовый вариант для обсуждения, не выбор библиотеки.

## Вход и извлечение

PROPOSED: первый проверочный корпус — разрешённые UTF-8 TXT/MD, в том числе синтетические. MD извлекается как текст с сохранением заголовков; сложные таблицы, PDF, DOCX, OCR и изображения не обещаны. После получения образцов выбрать необходимые адаптеры. Не заменять реальные документы искусственными в итоговом предметном эксперименте без объяснения ограничения.

Оператор явно задаёт перечень входов. Проверяются формат, декодирование, размер, непустой извлечённый текст и разрешённость использования. Все документы перечислены в BuildReport. Для одинаковых байтов предлагается один Document с сохранением входных имён; почти одинаковые тексты автоматически не объединяются.

Базовая очистка: убрать UTF-8 BOM, привести окончания строк к LF, сохранить содержимое и номера строк извлечённого текста. Не удалять цены, номера, даты, отрицания, таблицы и строки как «шум» без отдельного правила и проверки. Исходные байты не переписывать. Обработка ошибок — BEH-INDEX-002.

## Разбиение и локаторы

PROPOSED baseline: блок — непустой абзац, граница — одна или несколько пустых строк. Каждый блок образует фрагмент, если его объём <= CHUNK_MAX_SEARCH_TOKENS. Не объединять абзацы автоматически в первой конфигурации. Если блок длиннее, разбить последовательными окнами по search tokens с шагом `CHUNK_MAX_SEARCH_TOKENS − CHUNK_OVERLAP_SEARCH_TOKENS`.

Ограничения: max > 0, 0 <= overlap < max; предложенный стартовый overlap=0, число max ещё не выбрано (OPEN-008). Абзац без search tokens не индексируется; это явно отражается в отчёте. Перекрытие — исследовательская настройка, не обязательная функция.

Текст окна определяется границами исходных токенов: первое начинается с начала блока, прочие — с начала своего первого токена; конец промежуточного окна — начало следующего токена после последнего включённого, последнего — конец блока. Так сохраняются знаки после слов; overlapping-окна могут повторять текст. ordinal назначается по порядку документа. Локатор сохраняет диапазон строк и доступный заголовок; данные страницы только из соответствующего импортёра.

Риск baseline: ответ может требовать соседних абзацев или таблицы; это проверяется оценкой контекста. Изменение разбиения считается изменением pipeline и разметки, а не косметическим исправлением.

## Нормализация для поиска

Единый предложенный анализатор для документов/вопроса:

1. Unicode NFC и lowercase только поискового представления.
2. Токен — максимальная последовательность Unicode-букв или максимальная последовательность Unicode-цифр; прочие символы разделяют токены.
3. Сохранить «ё» отдельно от «е»; без скрытого преобразования.
4. Стоп-слова не удалять; stemming/лемматизацию в baseline не применять.
5. Отображаемый text хранить отдельно от search_tokens без lowercase.

Этот baseline — PROPOSED, SRC-003. Русская морфология, сокращения, дефисы и синонимы могут снижать recall; сравнение нормализаций предусмотрено в исследовании. Числа с пунктуацией могут стать несколькими search tokens, но исходные значения сохраняются в text.

## Идентичность и воспроизводимость

DRAFT, SRC-003:

- document_id — SHA-256 исходных байтов с однозначным префиксом типа сущности.
- chunk_id — SHA-256 канонически сериализованных document_id, pipeline_config_hash, ordinal и text_hash.
- index_version — SHA-256 канонического manifest-content: mode базы знаний, отсортированные документы/фрагменты/метаданные, конфигурация, schema/extractor/analyzer/BM25 versions. Благодаря mode снимки двух баз различаются даже при одинаковом составе документов.
- Порядок документов — document_id по возрастанию; внутри — ordinal. Timestamp и build_attempt_id не входят в hash версии.
- Каноническую сериализацию и версии зависимостей зафиксировать после OPEN-007; произвольный порядок ключей/файлов недопустим.

Смена текста, конфигурации или влияющих метаданных меняет снимок. Смена пути без смены байтов не меняет document_id; смена отображаемого title может изменить manifest/index_version. Фактические настройки копируются в manifest без секретов. Снимок включает исходные search tokens или возможность точно восстановить их.

## Сборка и публикация

1. Собрать артефакты в отдельное временное расположение внутри разрешённого workspace/data-каталога.
2. Проверить уникальность ID, соответствие hash, непустой корпус/индекс, связь каждого фрагмента с Document и каждый locator с text.
3. При отклонённом документе/сбое не публиковать снимок; сохранить отчёт. Явное исключение документа означает новый состав корпуса и новую попытку.
4. Публиковать целиком только валидный снимок. Не перезаписывать активный каталог частями.
5. Backend выбирает опубликованный снимок при запуске; переключение — контролируемый перезапуск, без web-upload и online-reindex.

Две базы знаний (ADR-004, DRAFT, SRC-003): шаги выполняются отдельно для базы каждого режима — свой перечень входов, свой отчёт и снимок. Сбой сборки одной базы не затрагивает опубликованный снимок другой. Входят ли одинаковые документы в обе базы и как распределять документы между ними, не определено (OPEN-010). Одинаковый document_id в двух базах допустим, потому что снимки не смешиваются.

Сохранённые старые снимки позволяют воспроизвести источник; при удалении API возвращает INDEX_VERSION_UNAVAILABLE. Срок хранения — OPEN-005. Сырые документы/индексы с закрытой информацией не добавляются в Git автоматически.

## Проверки и критерий готовности

TEST-RAG-001: фикстуры с заголовками, числами, отрицаниями, длинным абзацем, пустыми строками, BOM и кириллицей; text/locator сохраняют смысловые данные. TEST-INDEX-001: две сборки одинаковых входов дают одинаковые manifest-content/ID и retrieval. TEST-INDEX-002: неверное кодирование/формат/пустой документ/сбой записи не активируют снимок.

До реализации требуется согласовать формат, анализатор, chunking и конфигурацию. Успешный парсинг не доказывает, что извлечение пригодно для ответов: на реальных образцах нужна визуальная/экспертная проверка содержания.
