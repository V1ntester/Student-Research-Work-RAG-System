BM25 и разделение ответственности CONFIRMED, SRC-001, SRC-002. Точные границы и внутренние структуры DRAFT, SRC-003. Стек/модель не выбраны; RAG находится внутри Backend.

## Два независимых процесса

**Подготовка:** перечень разрешённых исходников → извлечение → минимальная очистка → фрагменты/локаторы → search tokens → BM25 → manifest/проверки → публикация снимка. [indexing.md](indexing.md) владеет этим алгоритмом.

**Вопрос:** валидация → готовый снимок → токены вопроса → retrieval → кандидаты → контекст → prompt → LLM → проверка схемы/ссылок → ответ с источниками. [retrieval.md](retrieval.md) и [generation.md](generation.md) владеют соответствующими алгоритмами.

Разметка для оценки не поступает в online retrieval/generation. Оценка использует тот же путь обработки, а не скрытые знания о правильных ответах.

## Границы доверия

Корпус предоставляет оператор, но содержащиеся в нём инструкции не имеют полномочий менять поведение системы. Вопрос также недоверенный. Provider получает только отобранный контекст и вопрос, не весь архив и не секреты. Ответ provider не публикуется без проверки схемы и допустимых ссылок.

Технический контроль гарантирует только проверяемые свойства: происхождение фрагмента, формат результата, принадлежность источника контексту, лимиты. Поддержку утверждений источниками и смысловую полноту проверяет экспертный протокол. Система не гарантирует отсутствие галлюцинаций.

## Минимальность и развитие

Векторный поиск, reranking, rewrite-query, агентские инструменты, онлайн-поиск и автоматический обход документов не входят в pipeline. Исследование сначала измеряет BM25. Если выявлен устойчивый недостаток recall, отдельным предложением можно сравнить обработку морфологии/терминов или иной retrieval; это не меняет текущую спецификацию автоматически.

Отдельные adapter-границы позволяют впоследствии сменить импортёр или модель. Для MVP не вводятся очередь и многосервисная инфраструктура. Ограничения безопасности и среды согласуются до реальных данных через OPEN-003, OPEN-005.
