# Оценка качества RAG

> **Простыми словами.** Как измерять качество: насколько хорошо находятся нужные фрагменты (считается автоматически по разметке эксперта) и насколько правильны и полны ответы (оценивает эксперт).

Необходимость отдельной оценки CONFIRMED, SRC-001, SRC-002. Метрики и процедура ниже PROPOSED, SRC-003; методические определения retrieval основаны на SRC-004. Порог успеха OPEN-006, объём и разметчики OPEN-009. Эксперименты ещё не проводились.

## Оценочный набор

Пример содержит case_id, самостоятельный вопрос, режим (база знаний, ADR-004), категорию, answerability, версию индекса, relevant_chunk_ids, ожидаемые факты/уточнение/конфликт, автора и split. Категории: ответ есть; ответ частичный; ответа нет; вопрос неоднозначен; сведения противоречат; термины не совпадают; документ содержит недоверенные инструкции.

Эксперт размечает по действительным фрагментам, а не по ответу системы. По возможности полный небольшой корпус просматривается для каждого вопроса; если использован только pool кандидатов, отметить неполноту разметки. После изменения chunking/корпуса проверить и перенести разметку, не использовать старые chunk_id молча.

Development-набор — для настройки; test — только итоговая оценка зафиксированного варианта. Близкие перефразировки и вопросы с одинаковым фактом группировать в одном split, чтобы уменьшить утечку. Вопросы эксперта не должны быть составлены только из удобных для BM25 формулировок.

## Retrieval и контекст

Для вопроса q: Rq — размеченные релевантные фрагменты; Tq — первые k результатов retrieval.

- Recall@k = |Rq ∩ Tq| / |Rq|, только для |Rq| > 0.
- Precision@k = |Rq ∩ Tq| / k, k фиксировано; отсутствующие позиции при выдаче короче k считаются неполезными. Если весь корпус меньше k, выбрать и объявить меньший k для эксперимента.
- Hit@k = 1, если есть хотя бы один релевантный фрагмент, иначе 0; полезно, когда достаточно одного основания.
- ContextRecall = |Rq ∩ Cq| / |Rq| для фактически переданного множества Cq. Дополнительно эксперт отмечает, достаточно ли Cq для полного ответа.
- Для вопросов без ответа отдельно считать долю случаев без пригодного контекста/с корректным отказом. Recall при пустом Rq — N/A, не 0 и не 1.

Метрики усреднять по вопросам, показывать число подходящих вопросов, знаменатель и разбивку по категориям. Базы знаний «Спросить» и «Продавать» оцениваются раздельно; общий агрегат допустим только вместе с раздельными значениями (PROPOSED, SRC-003). При неполной разметке назвать recall оценкой по доступным judgments, не полнотой по всему корпусу. [Методическая основа precision/recall](https://nlp.stanford.edu/IR-book/html/htmledition/evaluation-of-unranked-retrieval-sets-1.html).

MRR или nDCG можно добавить при реальной потребности различать позиции/степени релевантности; для первого исследования обязательного расширения нет. [Метрики ранжированных результатов](https://nlp.stanford.edu/IR-book/html/htmledition/evaluation-of-ranked-retrieval-results-1.html).

## Семантическая рубрика ответа

PROPOSED шкала 0/1/2, для нерелевантного критерия N/A:

| Критерий | 0 | 1 | 2 |
|---|---|---|---|
| Правильность | Существенно неверно | Есть неточность, не меняющая основное действие | Верно относительно разрешённого актуального корпуса |
| Полнота | Основная часть пропущена | Частично покрыты нужные факты | Покрыто всё, что требуется для данного исхода |
| Обоснованность | Существенные утверждения без оснований | Часть утверждений не подтверждена | Все проверяемые корпоративные утверждения поддержаны |
| Ссылки | Не подтверждают утверждения | Подтверждают часть | Соответствуют утверждениям и локаторам |
| Исход | Ошибочно отвечает/отказывает/выбирает объект | Недостаточно явно обозначен пробел | Корректно отвечает, уточняет или обозначает ограничение |
| Пригодность | Непонятно или мешает задаче | Требует заметного уточнения | Понятно и достаточно для разрешённой задачи |

Не усреднять опасную ошибку до «хорошего ответа»: эксперт отдельно отмечает существенную неподтверждённую цифру/условие, ложное обещание или неверный порядок действий. Что считать критической предметной ошибкой — NEEDS_DOMAIN_REVIEW, SRC-003, OPEN-006.

Отказы оценивать на вопросах без ответа и на вопросах с ответом отдельно: частые отказы могут скрывать низкое качество. Partial оценивается по правильности подтверждённой части и явности пробела. Conflict/clarification — по действительно необходимому ограничению. Семантическая разметка минимум одним экспертом, по возможности второй независимо проверяет часть; расхождения и способ разрешения сохранять.

## Технические измерения

Длительность retrieval, генерации и всего запроса, p50/p95 только при достаточном числе измерений с указанием N; доля успешных HTTP-результатов, ошибок, невалидных ссылок/схем, таймаутов; вызовы модели и стоимость только если доступна фактическая тарификация. Без измерений не писать «быстро» или «дёшево». Не смешивать штатный insufficient с технической ошибкой.

## Воспроизводимый запуск оценки

Зафиксировать dataset/split, корпус/индекс/config, окружение, библиотеку, prompt/model, параметры/seed и число повторов. Повторы LLM задаются до итоговой оценки; retrieval при одинаковых входах детерминирован. Для provider version без закрепления фиксировать доступный model ID и дату, ограничение воспроизводимости отразить явно.

Каждый пример сохраняет outcome, выбранные фрагменты и причины пропуска, технические метрики, оценки и примечания. Допустимость хранения текстов — OPEN-003, OPEN-005. Неуспешные запросы входят в отчёт; не исключать их ради повышения качества. Семантическую оценку среди успешно полученных ответов показывать вместе с coverage/ошибками по всем вопросам.
