# BM25 retrieval и отбор контекста

> **Простыми словами.** Как система ищет подходящие фрагменты по словам вопроса (алгоритм BM25) и как выбирает из найденного те, что поместятся в запрос к языковой модели.

BM25 как база CONFIRMED, SRC-001, SRC-002. Политика кандидатов/контекста DRAFT, SRC-003. Методическая основа SRC-004. Библиотека и численные настройки OPEN-007, OPEN-008.

## Контракт retrieval

Вход: самостоятельный question после валидации, неизменяемый снимок, зафиксированный analyzer/config. Выход: SearchHit[] с chunk_id, конечным числовым score и rank. Ошибка чтения/индекса — RetrievalError, не пустой массив.

Вопрос обрабатывается тем же анализатором, что документы. PROPOSED baseline: повторяющиеся query tokens для scoring считаются один раз; частоты терминов документа остаются частью BM25. Поддержку именно такого поведения выбранной библиотекой проверить; если она учитывает query frequency иначе, требуется явное изменение конфигурации/спецификации.

## Вариант BM25 и кандидаты

До APPROVED зафиксировать library/version, IDF-формулу, обработку query frequency, нормализацию длины и параметры k1/b. Название «BM25» недостаточно для одинаковых score у разных реализаций. Описание зависимости от частот и длины: [SRC-004](https://nlp.stanford.edu/IR-book/html/htmledition/okapi-bm25-a-non-binary-model-1.html).

Предлагаемая политика без произвольного порога уверенности:

1. Если search tokens вопроса пусты, кандидатов нет; допустимый вопрос из одной пунктуации не превращается в ошибку поиска.
2. Кандидат должен содержать хотя бы один search token вопроса; это проверяется отдельно от score.
3. Получить BM25-score для кандидатов; сортировать по убыванию, затем document_id по возрастанию и ordinal по возрастанию.
4. Возвратить первые RETRIEVAL_TOP_K; k > 0, согласуется в OPEN-008.
5. Не фильтровать автоматически по score > 0: у разных вариантов IDF допустимы нулевые/отрицательные значения даже при совпадении терминов. Политика IDF входит в manifest.

Нет reranking, векторного поиска, query rewrite или обращения в интернет. Детерминированный порядок и версия корпуса нужны для сравнения, а не только для логов.

## Отбор контекста

ARCH-RAG-003 получает кандидатов и исходный text, а не только токены. Предлагаемый алгоритм: идти по рангу; добавлять каждый целый фрагмент вместе с метаданными/разделителями, если он помещается в остаток бюджета; слишком большой пропустить и продолжить. Не дублировать chunk_id. Назначить S1… после окончательного отбора. Одночастный большой фрагмент нельзя молча обрезать и представить полным источником.

Бюджет вычисляется модельным tokenizer-ом: `input_limit − reserved_output − tokens(system/instructions/question/format/overhead)`. Все части учитываются через выбранный adapter; search tokens и модельные tokens — разные единицы. Ограничения OPEN-008 должны гарантировать, что при максимально допустимом вопросе остаётся место хотя бы для одного максимального фрагмента. Невалидная конфигурация не запускается; обнаруженная во время работы ошибка бюджета → INTERNAL_ERROR, не «нет знаний».

После настройки Budget проверки пустой Context при валидной конфигурации означает отсутствие пригодных кандидатов; Backend возвращает insufficient/no_candidates и не вызывает модель. Причины пропуска кандидатов фиксируются в исследовательском отчёте без утечки данных в обычные логи.

## Достаточность и ограничения

Lexical match не доказывает наличие ответа. Модель может вернуть insufficient_context/partial/clarification/conflict; semantic sufficiency не определяется единственным числовым порогом BM25. Настройку порога можно предложить отдельным экспериментом, не вводить без оценки.

Разница между retrieval и context selection измеряется: полезный фрагмент может быть найден, но не помещён. Низкий recall из-за терминологии или chunking не исправляется требованием к prompt. Вопросы с местоимениями без объекта остаются ограничением самостоятельного режима.

## Воспроизводимость и проверки

Зафиксировать query text, analyzer, corpus/index/config, query-frequency policy, k, tie-break и окружение. При идентичных входах обязателен один порядок chunk_id; при фиксированной библиотеке score сравнивать с явно заданным числовым допуском, если требуется. Между версиями библиотек совпадение не обещается.

TEST-RAG-002: совпадение одного/нескольких терминов, повторы query tokens, отсутствие совпадений, только пунктуация, частый термин с нулевым/отрицательным score, равные score и стабильный порядок, токен-бюджет с пропуском слишком большого фрагмента. Ожидания проверять на маленьком ручном корпусе, не только сравнением функции с самой собой.

Recall@k/Precision@k считаются на фрагментах по экспертным relevant_chunk_ids; качество фактически переданного контекста измеряется отдельно. Определения и обработка неполной разметки — [evaluation.md](evaluation.md).
