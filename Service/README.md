# Источники проекта и Domain Expert Review

Материалы Service — рабочие источники, не автоматические требования. Основание процесса: CONFIRMED, SRC-001. Детали шаблонов ниже DRAFT, SRC-003. Материалы и макет коллеги пока не получены.

## Папки

- `meetings/` — протоколы и заметки встреч с датой/участниками.
- `transcripts/` — исходные транскрипции; не исправлять слова собеседника молча.
- `domain-decisions/` — предметные решения и точная область их подтверждения.
- `references/` — исходное задание, макеты и разрешённые справочные материалы.

Пустые папки отмечены техническими `.gitkeep`; это не пустые спецификации. Не размещать закрытые документы в Git без разрешения владельца. Если материал доступен только вне репозитория, указать способ доступа и ограничения, не делать ложную локальную ссылку.

## Регистрация источника

Добавить SRC в [реестр](../docs/README.md): автор, дата получения, файл/ссылка, область сведений, степень подтверждения. Различать дату встречи и дату регистрации. Ссылка на документ не доказывает согласование. Заявление эксперта подтверждает только явно сказанное содержание; разрешение реализации остаётся отдельным.

## Domain Expert Review

1. Изучить макет/материалы как новые входные данные; сохранить исходник и provenance.
2. Выделить **факт**, **требование**, **предложение**, **неоднозначность**; у каждой записи точный фрагмент/страница/таймкод и автор.
3. Сопоставить с REQ/RULE/BEH/UI/API/ARCH; если соответствия нет, записать пробел.
4. Выявить конфликт, изменение scope или неполную информацию. Создать OPEN для спорного решения.
5. Подготовить таблицу «текущая спецификация → новое свидетельство → предлагаемая замена → причина → затронутые ID → статус».
6. Показать существенные изменения пользователю до перезаписи согласованных положений. Уточнять группами только нужные спорные решения; независимые исправления продолжать.
7. После подтверждения обновить продукт/правила и присвоить адресные статусы с источниками; не считать весь материал согласованным.
8. Синхронно актуализировать сценарии и UI по макету, затем API/данные/RAG и план тестов.
9. Обновить матрицу трассируемости и критерии исследования, если поменялись задачи/корпус.
10. Зафиксировать согласованное изменение в change-history, незавершённую часть в Update. Закрытый OPEN сохраняет историю решения.

## Компактный список вопросов коллеге

Ответы сейчас не требуются; список готов для будущей встречи.

| Тема | Что выяснить | Связи |
|---|---|---|
| Реальные задачи | Примеры частых и сложных вопросов, что менеджер делает после ответа, цена ошибки | GOAL-001/004; OPEN-001/006 |
| База знаний | Форматы/объём/язык/сканы/таблицы, примеры документов, владелец и обновления | OPEN-002/004 |
| Продажи | Типовые ситуации, допустимые сведения и ответы, существенные ошибки/противоречия | BEH-CHAT-005/011/012; OPEN-006 |
| Онбординг | Шаги новичка, критерии самостоятельности, текущая помощь наставника | GOAL-002/003; HYP-004/005 |
| Ожидаемый ответ | Краткое объяснение или порядок действий, обязательные основания, когда уточнять/отказывать | REQ-003/004/005 |
| Ограничения | Что можно передавать модели, кто видит документы, есть ли данные клиентов | OPEN-003/005 |
| Макет и процесс | Какие действия нужны на экране, требуется ли диалог, удобны ли источники | UI-CHAT-001…004; OPEN-001 |
| Оценка | Кто размечает и оценивает, какие задачи/участники доступны, критерий успеха | OPEN-006/009 |

## Шаблон записи предметного решения

Дата/автор; SRC и точная цитата/ссылка; классификация; затронутые ID; решение либо предложение; кто подтвердил и что именно; статус; остающиеся вопросы. При отсутствии явного подтверждения использовать NEEDS_DOMAIN_REVIEW или PROPOSED, не APPROVED.
